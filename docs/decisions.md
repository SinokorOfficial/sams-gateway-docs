# 설계 결정 기록 (ADR)

게이트웨이를 만들며 내린 결정과 그 이유입니다. 바꾸고 싶을 때는 여기 적힌 배경이 아직 유효한지부터 확인하세요.

| 번호 | 결정 | 상태 |
|---|---|---|
| ADR-001 | 서비스마다 포트를 열지 않고 정문 nginx 하나로 받는다 | 채택 |
| ADR-002 | 대표 도메인 하나에 사이트를 경로로 모은다 | 채택 |
| ADR-003 | 루트와 미등록 경로는 404, 색인 차단 | 채택 |
| ADR-004 | 서비스 연결은 호스트 포트 우선, 도커 네트워크는 필요할 때만 | 채택 |
| ADR-005 | upstream 은 `resolve` 로 동적 해석 | 채택 |
| ADR-006 | 배포는 검사 후 반영(`deploy.sh`), CI 없음 | 채택 |
| ADR-007 | HSTS 는 대표 도메인에만 | 채택 |
| ADR-008 | SamsApi 는 전용 도메인으로 단독 운영 | 채택 (DNS 전환 대기) |
| ADR-009 | 인증서는 하나에 이름을 추가, webroot 검증 | 채택 |

## ADR-001 · 정문 nginx 하나

**배경** 같은 VM 에 서비스가 늘면서 서비스마다 포트를 열고(8400, 8500, …) 각자 TLS 를 처리했습니다. 방화벽 규칙이 늘고, 인증서 갱신 대상도 서비스마다 생겼습니다.

**결정** 외부 80·443 은 게이트웨이만 엽니다. TLS 는 게이트웨이에서 끝내고 서비스로 넘깁니다.

**결과** 방화벽은 80·443 만 관리합니다. 대신 게이트웨이가 단일 장애점이 되므로 설정을 단순하게 유지하고 반영은 항상 검사를 거칩니다(ADR-006).

## ADR-002 · 경로로 모으기

**배경** 사이트마다 서브도메인을 쓰면 DNS 등록과 인증서 이름 추가가 사이트마다 필요합니다.

**결정** 대표 도메인 하나 아래에 `/svc/`, `/hr/` 처럼 경로로 사이트를 붙입니다.

**결과** 새 사이트는 location 추가만으로 됩니다. 대신 서비스가 하위 경로에서 동작해야 하고(상대경로), 같은 도메인의 사이트끼리 브라우저 저장소·쿠키가 분리되지 않습니다. 아주 민감한 서비스는 서브도메인을 고려합니다.

## ADR-003 · 아무것도 알려 주지 않기

**결정** 대표 도메인의 루트와 등록되지 않은 경로는 404 를 돌려주고, `X-Robots-Tag: noindex` 와 `robots.txt` 로 색인을 막습니다. 사이트 목록 페이지를 두지 않습니다.

**결과** 스캐너나 검색엔진이 어떤 사이트가 있는지 알 수 없습니다. 사용자는 정확한 주소(예: `/svc/app`)로 들어와야 합니다.

## ADR-004 · 호스트 포트 우선

**배경** 처음에는 게이트웨이를 서비스의 도커 네트워크에 붙였습니다. 그러자 서비스 쪽 `docker compose down` 이 게이트웨이 연결을 끊고, 게이트웨이 compose 가 서비스 네트워크 존재에 의존하게 되었습니다.

**결정** 서비스가 호스트 포트를 열 수 있으면(방화벽은 닫은 채) `host.docker.internal:<포트>` 로 찾아갑니다. SamsApi 가 이 방식입니다. 도커 네트워크는 서비스가 호스트 포트를 열기 어려울 때만 씁니다(인증서 관리 서비스).

**결과** 서비스와 게이트웨이를 서로 독립적으로 내리고 올릴 수 있습니다.

## ADR-005 · upstream resolve

**배경** nginx 는 기본적으로 시작 시 한 번만 upstream 이름을 해석해, 서비스 재배포로 컨테이너 IP 가 바뀌면 502 가 납니다.

**결정** 도커 네트워크로 붙는 upstream 은 `zone` + 도커 DNS `resolver 127.0.0.11 valid=5s` + `server … resolve` 를 씁니다. 이 기능 때문에 nginx 1.27.3 이상을 씁니다.

**결과** 서비스 재배포 때 게이트웨이를 건드리지 않습니다.

## ADR-006 · 검사 후 반영

**배경** 잘못된 설정으로 컨테이너가 재생성되면 정문 전체가 멈춥니다. 변경 빈도는 낮아 CI 를 둘 이유는 적습니다.

**결정** `deploy.sh` 가 VM 임시 폴더에 올린 새 설정을 운영과 같은 조건의 임시 컨테이너에서 `nginx -t` 로 검사하고, 통과할 때만 반영 후 reload 합니다.

**결과** 검사 조건이 운영과 다르면 정상 설정도 검사에서 막힐 수 있습니다(실제로 한 번 있었고, 운영은 안전하게 유지됨). 게이트웨이 compose 를 바꾸면 검사 명령도 함께 맞춥니다.

## ADR-007 · HSTS 범위

**결정** 대표 도메인에는 HSTS 1년을 겁니다. SamsApi 전용 도메인에는 걸지 않습니다.

**이유** SamsApi 는 같은 이름의 평문 주소(`http://…:8400`)를 쓰는 사용자가 남아 있어, HSTS 를 걸면 브라우저가 https 로 바꿔 접속이 깨집니다. 평문 사용자가 없어진 뒤 추가를 검토합니다.

## ADR-008 · SamsApi 단독 도메인

**결정** SamsApi 는 사이트 모음에 넣지 않고 전용 도메인을 씁니다. 그 도메인에는 다른 사이트를 붙이지 않습니다.

**배경** 2026-10-21 운영 결정. SamsApi 는 사내 여러 시스템이 직접 호출하는 API 라 사이트 모음과 섞지 않습니다.

**결과** 업로드 크기·시간 제한 같은 정책을 SamsApi 에 맞춰 따로 둘 수 있고, 사이트 모음 쪽 변경이 API 호출에 영향을 주지 않습니다.

**상태** 서버 블록과 임시 인증서는 준비됐고, DNS 를 VM 으로 옮기면 바로 동작합니다.

## ADR-009 · 인증서 하나에 이름 추가

**결정** 대표 도메인 인증서 하나에 필요한 이름을 SAN 으로 추가하고(`--expand`), HTTP-01 webroot 로 검증합니다. certbot 은 VM 에 설치하지 않고 컨테이너로 실행합니다.

**결과** 갱신 cron 이 하나뿐이고 게이트웨이를 멈추지 않고 갱신됩니다. 대신 80 포트와 검증 location 이 항상 살아 있어야 합니다.
